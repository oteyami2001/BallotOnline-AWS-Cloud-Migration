# ⚙️ Infrastructure as Code — AWS CloudFormation

The BallotOnline target environment is defined as seven CloudFormation stacks. Together they build the network, security, database, and migration resources shown in the [target architecture](../../architecture/migration-architecture.md), so the environment can be recreated, reviewed, and version-controlled instead of being built by hand in the console.

![BallotOnline AWS target architecture](../../architecture/diagrams/aws-target-architecture.svg)

---

## 📦 Stacks

| # | Template | Stack Name | Creates |
|---|---|---|---|
| 1 | [`01-network.yaml`](01-network.yaml) | `ballotonline-network` | VPC across 2 AZs; public, app, DB, and MGN staging subnets; Internet and NAT gateways; route tables; optional Site-to-Site VPN; VPC Flow Logs |
| 2 | [`02-security.yaml`](02-security.yaml) | `ballotonline-security` | Security groups for each workload, customer-managed KMS key with rotation, EC2 instance profile for Systems Manager, DMS service roles |
| 3 | [`03-aurora.yaml`](03-aurora.yaml) | `ballotonline-aurora` | Encrypted Aurora MySQL cluster, writer + Multi-AZ reader, TLS required, password managed by Secrets Manager |
| 4 | [`04-dms.yaml`](04-dms.yaml) | `ballotonline-dms` | Private DMS replication instance, endpoints `ccs640mysql` and `ccs640target`, task `ccs640migration` |
| 5 | [`05-governance.yaml`](05-governance.yaml) | `ballotonline-governance` | Multi-Region CloudTrail (encrypted, validated, TLS-only bucket, CloudWatch Logs delivery), GuardDuty, IAM Access Analyzer, optional Security Hub |
| 6 | [`06-monitoring.yaml`](06-monitoring.yaml) | `ballotonline-monitoring` | Encrypted SNS alert topic, Aurora/DMS/VPN/EC2 alarms, CIS-style security alarms on CloudTrail, EventBridge rules, operations dashboard |
| 7 | [`07-operations.yaml`](07-operations.yaml) | `ballotonline-operations` | Systems Manager patch scan and install, inventory, CloudWatch agent install and configuration |

Stacks share values through **CloudFormation exports** named `<EnvironmentName>-<Value>`, so they must be deployed in order:

```text
01-network ──▶ 02-security ──▶ 03-aurora ──▶ 04-dms
   VPC, subnets      SGs, KMS, IAM      cluster, secret     endpoints, task

05-governance   (independent: audit logging and threat detection)

03-aurora + 05-governance ──▶ 06-monitoring        07-operations (independent)
```

## 🔐 Security Built In

| Control | Where |
|---|---|
| No public IPs on workloads, DB, or DMS | All stacks; private subnets only |
| One security group per workload, only required ports | `02-security.yaml` |
| Aurora reachable only from the intranet tier and DMS | `AuroraSecurityGroup` uses security-group references, not CIDRs |
| DMS has **no inbound rules** and restricted outbound | `DmsSecurityGroup` |
| Encryption at rest with a customer-managed KMS key (rotation on) | Aurora storage, Performance Insights, DMS storage |
| TLS required for all database connections | `require_secure_transport = ON`; DMS endpoints use `SslMode: require` |
| No passwords in templates | Aurora password generated by Secrets Manager; DMS reads credentials with dynamic references at deploy time |
| Network audit trail | VPC Flow Logs → CloudWatch Logs (90-day retention) |
| API audit trail and threat detection | CloudTrail with log file validation, GuardDuty, Access Analyzer |
| Server access without SSH/RDP | `AmazonSSMManagedInstanceCore` instance profile for migrated EC2 instances |
| Data protection | Aurora `DeletionPolicy: Snapshot`, deletion protection, 7-day backups; KMS key retained |

## ✅ Prerequisites

- AWS CLI v2 with credentials that can create VPC, IAM, KMS, RDS, and DMS resources
- For the DMS stack:
  - Source MySQL prepared with [`source-preparation.sql`](../../database-migration/mysql/source-preparation.sql)
  - A Secrets Manager secret holding the source DMS user's password:

    ```bash
    read -rs -p "Source DMS password: " PW; echo
    aws secretsmanager create-secret \
      --name ballotonline/source-mysql/dms \
      --secret-string "{\"password\":\"${PW}\"}"
    unset PW
    ```
  - Network path from the DMS subnets to the source (Site-to-Site VPN, `CreateVpn=true`)

## 🚀 Deploy

[`deploy.sh`](deploy.sh) deploys the stacks in order with `aws cloudformation deploy`.

```bash
export AWS_REGION=us-east-1

# Network, security, governance, and Aurora
./deploy.sh deploy all

# GuardDuty or Access Analyzer already enabled in the account?
ENABLE_GUARDDUTY=false ./deploy.sh deploy governance

# Optional: with the Site-to-Site VPN
CREATE_VPN=true CUSTOMER_GATEWAY_IP=<office-public-ip> ON_PREM_CIDR=192.168.0.0/16 \
  ./deploy.sh deploy network

# DMS (needs the source MySQL host reachable over the VPN)
SOURCE_SERVER_NAME=<mysql-private-ip> ./deploy.sh deploy dms

./deploy.sh status
```

### After deployment

```bash
# 1. Test both endpoints (the step that caught DMS-00001 in the project)
aws dms test-connection --replication-instance-arn <ARN> --endpoint-arn <SOURCE_ARN>
aws dms test-connection --replication-instance-arn <ARN> --endpoint-arn <TARGET_ARN>
aws dms describe-connections --filters Name=endpoint-arn,Values=<SOURCE_ARN>

# 2. Start the migration task
aws dms start-replication-task --replication-task-arn <TASK_ARN> \
  --start-replication-task-type start-replication
```

Then validate with [`validation-queries.sql`](../../database-migration/aurora/validation-queries.sql).

### Key parameters

| Stack | Parameter | Default | Notes |
|---|---|---|---|
| network | `SingleNatGateway` | `true` | `false` adds a second NAT gateway for AZ resilience (higher cost) |
| network | `CreateVpn` / `CustomerGatewayIp` | `false` / — | Site-to-Site VPN to the office |
| network | `OnPremisesCidr` | `192.168.0.0/16` | Used in security group rules |
| aurora | `InstanceClass` | `db.t4g.medium` | Smallest Aurora MySQL 8.0 class |
| aurora | `CreateReader` | `true` | Reader in AZ B for automatic failover |
| dms | `MigrationType` | `full-load` | Matches the project; `full-load-and-cdc` for minimal downtime |
| dms | `SourceServerName` | — | **Use the private IP** unless DNS forwarding is configured (see below) |

## 🧠 Design Notes

**DNS and the DMS-00001 lesson.** The DMS replication instance resolves names with the VPC's Amazon Route 53 Resolver, which does not know on-premises hostnames. That is exactly what causes *"MySQL server host name could not be resolved"*. Either set `SourceServerName` to the server's private IP, or add a **Route 53 Resolver outbound endpoint** with a forwarding rule for the on-premises domain.

**Why the DMS task lives in CloudFormation.** Endpoint names, table mappings, and task settings are versioned with the rest of the environment. The mappings in the template match [`table-mappings.json`](../../database-migration/aws-dms/table-mappings.json).

**What is not in these templates.** EC2 instances for the Intranet, FTP, and NTP servers are created by AWS MGN at test and cutover launch (see [server migration](../../server-migration/hyper-v-to-aws/)). Their launch templates reference the security groups and the `ballotonline-ec2-managed` instance profile exported here.

**Retained resources.** The KMS keys and the CloudTrail log bucket are retained, and the Aurora cluster leaves a final snapshot, when their stacks are deleted. Audit logs outlive the environment on purpose. Delete them by hand when they are no longer needed.

## 🧹 Tear Down

NAT gateways, Aurora, and the DMS instance bill by the hour. Remove everything when finished:

```bash
./deploy.sh delete all     # operations → monitoring → dms → aurora → governance → security → network
```

The script turns off Aurora deletion protection after asking for confirmation.
