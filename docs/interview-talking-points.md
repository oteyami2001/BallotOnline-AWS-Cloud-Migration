# 🎤 Interview Talking Points

Preparation notes for Cloud Engineer interviews about the BallotOnline migration. Each point uses **STAR** (Situation, Task, Action, Result). Keep answers to about two minutes, and be precise about what was done in the course lab and what was built afterwards for this portfolio.

> **Honesty rule:** say "in the course lab" for DMS work actually performed, "I designed / implemented as code" for repository work, and "I would" for production recommendations. Never say the full environment was deployed to production. It wasn't.

---

## 1. Project Objective

- **Situation:** BallotOnline ran its HR database (MySQL) and Intranet, FTP, and NTP servers on a single Hyper-V host on premises. There was no high availability, administration was manual, and logging was limited.
- **Task:** Plan and carry out a migration to AWS that improves availability, security, and operations without disrupting HR work.
- **Action:** Assessed the workloads, picked a strategy for each, designed the target VPC, ran AWS DMS in the course lab, then built the full design as code: seven CloudFormation stacks, scripts, runbooks, and CI.
- **Result:** A complete, reviewable migration design and toolkit: architecture, migration procedures, security, monitoring, cutover, and DR, all validated automatically on every change.

## 2. Architecture Decision

- **Situation:** HR data is sensitive, and the office needs private access.
- **Task:** Design a target that is secure, highly available, and not over-built.
- **Action:** A VPC across two AZs with private app and DB subnets, no public IPs on workloads, a Site-to-Site VPN, and Aurora with a writer and reader in different AZs. I used a single NAT gateway by default to control cost, with a parameter for one per AZ.
- **Result:** It survives the loss of one AZ for the database, keeps internal services off the internet, and every choice is documented in [design decisions](../architecture/migration-architecture.md#11-key-design-decisions).

## 3. Replatform vs. Rehost

- **Situation:** Two very different workloads: a database, and three general-purpose servers.
- **Task:** Choose the lowest-risk path for each.
- **Action:** **Replatformed** MySQL to Aurora MySQL. It's compatible, so the application doesn't change, and AWS takes over backups, patching, and failover. **Rehosted** the servers with AWS MGN, because they're simple and refactoring them would add risk without much benefit. Modernization comes after migration: Amazon Time Sync replaces NTP, Transfer Family replaces FTP, and the Intranet moves behind a load balancer with Auto Scaling.
- **Result:** The effort goes where it adds value, and the migration path for each workload is easy to justify.

## 4. DMS Troubleshooting

- **Situation:** In the course lab, the DMS source endpoint failed. The assessment reported an ODBC connection error, then `DMS-00001` (host name could not be resolved). Later the task stopped with **"No tables were found at task initialization."**
- **Task:** Find out why DMS couldn't reach or read the source.
- **Action:** Worked through the layers: source availability, credentials, routing and security rules, then DNS. The replication instance resolves names inside AWS, not with the on-premises DNS. For the table error, checked the schema name in the table-mapping rule, the migration user's grants, and the task logs.
- **Result:** The lesson: test endpoints and DNS from where DMS runs, and validate mappings and grants before starting a task. The repository builds this in. It uses the source's private IP or a Route 53 Resolver outbound endpoint, has a [mapping file](../database-migration/aws-dms/table-mappings.json) with an exact schema name, a [`SHOW GRANTS` check](../database-migration/mysql/source-preparation.sql), and endpoint tests as a blocking go/no-go item.
- *If asked "did you fix it?"*, describe what you actually verified in the lab, and say the repository encodes the fixes and checks.

## 5. Security Design

- **Situation:** HR records are PII and are moving to a new environment.
- **Task:** Protect the data during and after migration.
- **Action:** Least-privilege IAM with MFA enforced by policy; a migration-operator policy limited to tagged resources, with explicit denies; one security group per workload, with Aurora reachable only from the app tier and DMS; KMS encryption; TLS required on Aurora; passwords generated by Secrets Manager; CloudTrail, GuardDuty, and Access Analyzer; Session Manager instead of SSH or RDP.
- **Result:** Defense in depth, with every control traceable to a template line ([security controls](../security/security-controls.md)). The policies were linted with Parliament.

## 6. Infrastructure as Code

- **Situation:** Building this by hand in the console would be error-prone and impossible to review.
- **Task:** Make the environment repeatable and reviewable.
- **Action:** Seven CloudFormation stacks (network, security, governance, Aurora, DMS, monitoring, operations) connected by exports; a `deploy.sh` that deploys in order and tears down in reverse; GitHub Actions running `cfn-lint`, `shellcheck`, syntax checks, and link checks.
- **Result:** The whole environment can be reviewed in a pull request and rebuilt for DR. **Be clear:** the templates are statically validated, not deployed to a live account.

## 7. Monitoring

- **Situation:** Without monitoring, migration problems go unnoticed until users report them.
- **Task:** Detect database, migration, server, and security problems early.
- **Action:** 22 CloudWatch alarms. Native metrics cover Aurora, DMS, VPN, and EC2, with auto-recover on host failure. CIS-style security alarms come from CloudTrail metric filters. EventBridge rules catch GuardDuty findings, Aurora failover, and DMS task state. The CloudWatch agent, installed through Systems Manager, adds memory and disk metrics, which EC2 doesn't report on its own.
- **Result:** One dashboard and an alert topic, plus a daily-to-quarterly [operating model](../monitoring/postmigration-operations.md).

## 8. Cutover and Rollback

- **Situation:** Cutover is where migrations usually fail.
- **Task:** Make the switch controlled and reversible.
- **Action:** A T-7 days → T+24 hours [runbook](../cutover-rollback/cutover-runbook.md); a [go/no-go](../cutover-rollback/go-no-go-checklist.md) where any unresolved blocking item means NO-GO; writes frozen before the final sync; validation before switching DNS; source kept intact until the rollback window closes.
- **Result:** The key insight: **rollback is only a DNS switch until users write to Aurora.** After that, the data has to be reconciled, through reverse DMS or a targeted replay. That's why the plan has a decision deadline.

## 9. What I Would Change for Production

- Deploy the stacks to a **sandbox account** first and run the full cutover rehearsal.
- Use **Full Load + CDC** instead of Full Load only, to minimize downtime.
- Set up **reverse replication** in advance, if the business needs a rollback option after go-live.
- Add **AWS Backup** plans with cross-Region copies, and agree RTO/RPO with the business, then test against them.
- Add **VPC interface endpoints** for Systems Manager and Secrets Manager, to reduce reliance on NAT.
- Use **multi-account** structure (AWS Organizations, SCPs, IAM Identity Center) instead of IAM users.
- Modernize after the move: Amazon Time Sync for NTP, Transfer Family for FTP, ALB + Auto Scaling for the Intranet.

## Quick Answers

| Question | Short answer |
|---|---|
| "What was the hardest part?" | DMS connectivity: DNS resolution and table selection. They taught me to validate the path and the mappings before starting a migration task. |
| "Why Aurora over RDS MySQL?" | Multi-AZ storage with fast failover, read replicas sharing storage, and storage that grows automatically, while staying MySQL-compatible. |
| "Why MGN?" | Block-level continuous replication, non-disruptive test launches, and a short cutover window, with no changes to the servers. |
| "Was it deployed?" | DMS was run in the course lab. The full environment exists as validated code and runbooks, not as a production deployment. |
| "How do you know the data is correct?" | Exact row counts, content hashes, spot checks, and DMS row-level validation, compared source vs. target before cutover. |
